# Security

How ClassHub protects accounts, tenants and student data **as implemented** at the end of Release 0. The target design is [ROADMAP.md](ROADMAP.md) B.5 and C.6–C.8.

## Reporting a vulnerability

Use GitHub's private vulnerability reporting on this repository. Do not open a public issue.

## Threat model (Release 0)

### Assets

| Asset | Where | Why it matters |
|---|---|---|
| Account credentials and sessions | `AspNetUsers` (PBKDF2 hashes), `.ClassHub.Auth` cookie, Data Protection keys (`DataProtectionKeys`) | Account takeover gives access to a teacher's whole workspace |
| Email tokens (confirmation, password reset) | Generated by Identity, sent in emails, carried in URL fragments | A leaked reset token is an account takeover |
| Workspace (tenant) data | `Workspaces`, `WorkspaceMembers`; later students, lessons, payments | Teachers' business and their students' personal data (minors included, later phases) |
| Platform roles | `AspNetUserRoles` (`PlatformOwner`, `PlatformAdmin`) | Platform-wide administration |
| Audit log | `AuditLog` | Evidence of who changed what; must not be forgeable or hold secrets |
| Outgoing email | `EmailOutbox`, `DevMailbox` | Tokens and personal data in transit |
| Repository and CI | GitHub repository (public), Actions, ruleset, PR gate | Supply chain: what reaches `main` reaches production later |

### Actors

| Actor | Trust | Can |
|---|---|---|
| Anonymous visitor / attacker on the internet | None | Call anonymous endpoints (register, login, confirm, resend, forgot, reset, antiforgery, health), the SPA, later public sites |
| Teacher (authenticated) | Own workspace only | Workspace APIs of workspaces they are an active member of |
| Another teacher (authenticated attacker) | Own workspace only | Everything a teacher can, aimed at someone else's workspace ids |
| Platform Owner/Admin | Platform operations only | No workspace access (by design); admin features arrive in R1-P9 with MFA |
| Operator with local shell access | Full (machine) | CLI `grant-platform-owner`, database, configuration; out of scope for the web threat model |
| Contributors and automation (Claude Code, Codex, Dependabot) | Through PRs only | Branches and PRs; `main` only through the ruleset (required checks, PR gate, no bypass) |

### Trust boundaries

1. **Browser ↔ API** (HTTP, same origin): everything from the browser is untrusted: bodies, route values, headers, cookies. Authentication by cookie, CSRF protection by the antiforgery header, input validated by FluentValidation, errors as ProblemDetails without internals.
2. **Authenticated user ↔ workspace**: the workspace id in the route is a request, not a grant; membership is verified per request and isolation is enforced in the database layer (filters, interceptor, composite FKs).
3. **API ↔ SQL Server**: EF Core with parameters only; raw SQL is allow-listed and parameterized; locally Windows authentication (accepted risk below), in tests and E2E disposable containers only (guards).
4. **API ↔ email**: outbox in the same transaction; only the dev mailbox in Development/Testing/E2E; email content HTML-encoded.
5. **Developer machine / CI ↔ `main`**: ruleset with required checks, the PR gate (commit-bound Codex evidence), secret scanning with push protection, gitleaks, dependency audits.

### Threats and mitigations

| Threat (STRIDE) | Example | Mitigation | Verified by |
|---|---|---|---|
| Spoofing: credential stuffing / brute force | Many passwords for one email | Lockout (5 attempts / 15 min), `auth` rate limit per IP, uniform 401 | `AuthFlowTests`, `PlatformPipelineTests` |
| Spoofing: account enumeration | Register/forgot/reset reveal existing emails | Identical 202/400 answers, dummy hash timing, token checked before password rules | `AuthFlowTests` |
| Spoofing: stolen reset/confirmation token | Token in logs, Referer or history | Tokens only in URL fragments (never sent to servers), removed from the address bar after reading, short lifetimes, single use (security stamp) | `AuthFlowTests`, Vitest |
| Spoofing: session fixation / stale sessions | Old cookie after password reset or suspension | Security stamp revalidation (60 s), stamp rotation on reset/role change, sign-out on suspension | `AuthFlowTests`, `PlatformOwnerCommandTests` |
| Tampering: CSRF | Another site posts to `/api/...` with the cookie | Antiforgery header required on unsafe requests (token bound to the user, in memory only), `SameSite=Lax` cookie | `AuthFlowTests`, `PlatformPipelineTests` |
| Tampering / information disclosure: cross-tenant access | Teacher B calls `/api/w/{A}` or crafts ids in bodies | Membership policy (404), named query filters (fail closed), save interceptor, composite tenant FKs, bypass allow-list | Isolation kit, `TenancyProbeTests`, `TenantBypassTests`, Playwright |
| Elevation of privilege: becoming Platform Owner | HTTP route to grant roles | Grant only through the local CLI (serialized, audited); no HTTP route | `PlatformOwnerCommandTests` |
| Elevation of privilege: missing authorization on a new endpoint | Endpoint without a policy | Deny-by-default fallback + metadata test that fails without `AllowAnonymous` or a named policy | `EndpointAuthorizationMetadataTests` |
| Information disclosure: errors and logs | Stack traces, SQL, emails, tokens in logs | ProblemDetails with `code`/`traceId` only; Serilog redaction of secrets, masked emails | `PlatformPipelineTests`, `ErrorAndValidationTests`, `SensitiveDataRedactionEnricherTests` |
| Information disclosure: dev-only surfaces in production | Dev mailbox lists every email | Mapped only in Development/Testing/E2E (API and SPA route) | `EnvironmentSurfaceTests` |
| Tampering: test environments hitting the real database | E2E or integration tests on `ClassHubDb` | `TestDatabaseGuard`, `DockerEndpointGuard`, `E2EDatabase.AssertDisposable` | `EnvironmentSurfaceTests`, fixture guards |
| Tampering: XSS / injection | Script in a workspace name, SQL in input | React escaping (no `dangerouslySetInnerHTML`), HTML-encoded emails, CSP, parameterized SQL | Review, `PlatformPipelineTests` (CSP) |
| Tampering: open redirect | `/login?returnTo=https://evil` | `safeReturnTo` accepts only same-site paths | Vitest |
| Denial of service | Request floods, huge bodies | Global per-IP limit on `/api`, named limits, 1 MB body limit | `PlatformPipelineTests` |
| Repudiation | "I did not change the settings" | Append-only audit log with actor and request id | `WorkspaceTenancyTests` |
| Supply chain | Malicious dependency, unreviewed code on `main` | Locked restores, central versions, pinned actions, Dependabot, audits, CodeQL, gitleaks, ruleset without bypass | CI |
| Tampering: faked review evidence | A PR body with hand-typed "clean" Codex evidence, or a PR that edits the gate workflow | Evidence signed with an Ed25519 key that exists only on the developer machine (public key in the repo); the gate runs on `pull_request_target` from the base branch without PR code and publishes the required status `classhub/codex-evidence` (fork workflows cannot create it) | `pr-gate.test.mjs` (unsigned, foreign key, edits after signing) |

### Residual risks (accepted for Release 0)

- MFA for platform roles is not implemented yet (R1-P9); no admin features exist until then.
- Email delivery is local only (dev mailbox); a real provider and its SPF/DKIM setup come with hosting.
- The local runtime identity is the developer's Windows account (sysadmin); production identity is decided with hosting (D-28).
- Codex reviews run on the developer machine; CI verifies the signed evidence but cannot re-run Codex. Whoever controls the machine holding the private evidence key can sign evidence; the key never leaves that machine (R0-P8 decision: signed local attestation instead of a paid CI integration or mandatory human approvals).
- Collaborators with write access can push branches whose workflows have a write token and could set commit statuses; today the only writer is the owner (and automation on the owner's machine).

## Authentication (R0-P4)

ASP.NET Core Identity with cookie sessions. See [ARCHITECTURE.md](ARCHITECTURE.md#accounts-and-sessions-r0-p4): PBKDF2 hashes, lockout, no account enumeration, security-stamp revalidation (60 s), Data Protection keys in the database, tokens only in URL fragments, antiforgery tokens bound to the signed-in user.

## Authorization: deny by default

- Fallback policy: authenticated user. It also applies to requests that match no endpoint.
- Every endpoint declares `AllowAnonymous` or a **named** policy (`EndpointAuthorizationMetadataTests`).
- Policies: `Authenticated`; workspace policies `ws:<permission>` (for example `ws:workspace.read`). Permissions are code constants (`WorkspacePermissions`), mapped from workspace roles (`WorkspaceRolePermissions`; today `Owner` has all workspace permissions). Unknown permission names fail when the policy is resolved.
- Platform roles (`PlatformOwner`, `PlatformAdmin`) are Identity roles. **They grant no workspace access**: a platform admin without membership gets 404 on workspace routes (tested). The first Platform Owner is created only with the local CLI `dotnet run --project src/ClassHub.Api -- grant-platform-owner <email> [--force-add]` (audited, never exposed over HTTP). The owner check, the grant, the session revocation and the audit entry run in one transaction under an application lock (`sp_getapplock`), so concurrent bootstraps cannot both add an owner without `--force-add`.

## Public leads (R1-P5)

- The public endpoints are anonymous and use no cookies (the island sends `credentials: 'omit'`); the answer is always `202 {received: true}`, so nothing submitted is reflected, and spam gets the same answer (no oracle).
- Spam protection (D-19): honeypot field, minimum fill time measured from a signed, site-bound form token (24 h), per-IP `public-form` limit, per-site hourly limit, length limits on every field. CAPTCHA is decided with hosting.
- Validation is server-side: offers must be public, active and of this teacher; subjects must be the teacher's; consent and the age/guardian confirmation (D-18, provisional text, configurable threshold) are required and their version is stored with the time.
- Intake checks run under the read-only public binding; the insert happens in its own scope with an explicit workspace (composite FKs keep offers and notes in the same workspace at the database level).
- The teacher's notification email carries no visitor data (only a link to the inbox, which requires a session); unconfirmed accounts can neither publish nor receive leads (D-10b).

## Public sites (R1-P4)

- Only **published** sites of **visible** owners (active owner membership, account not suspended) are public; everything else is a 404 with `noindex`. Hidden sections, unpublished drafts, non-public/inactive/archived offers and private profile fields never reach a template: the render model is an allow-list (snapshot-tested), and anonymous requests are bound to the workspace **read-only** (any tenant-owned write throws).
- Strict CSP for public pages (`PublicPageContentSecurityPolicy`): `default-src 'none'`, same-origin scripts (islands) and stylesheets only, no inline script or style, `frame-ancestors 'none'` (+ `X-Frame-Options: DENY`). Teacher text is Razor-encoded; JSON-LD is serialized with an encoder that escapes `<`, `>` and `&`, so it cannot close its script element (tested with `</script>` payloads). Island props travel as attribute-encoded JSON and are parsed, never evaluated.
- Absolute URLs (canonical, Open Graph, sitemap, robots) come from `App:PublicBaseUrl`, never from the request's Host header, so cached pages cannot be poisoned with another host.
- Output cache: only anonymous GET 200 responses without `Set-Cookie`; signed-in requests neither read nor fill it; nothing on a public page depends on the viewer; previews are never cached (`no-store`, no policy). Query strings do not create new cache entries. Evictions follow every change that shows on a page, and suspension evicts all site pages.
- The public photo is served only while the published hero shows it (`Cache-Control: public, max-age=3600`, versioned URL); the private profile photo endpoint still requires a member session.
- Page views (D-32) store a per-day counter only: no cookies, IP addresses, user agents or visit records. Public reads are rate-limited (`public-read`).

## Site preview (R1-P3)

- The preview URL carries a Data Protection token (authenticated encryption) naming one site, its workspace and the requesting member, valid 15 minutes. Invalid, tampered or expired tokens get a plain 404; the member's active membership is re-checked on every view before the request is bound to the workspace.
- The page is read-only, Razor-encoded (draft text is never HTML), `noindex, nofollow, noarchive` (meta + header), `no-store`, `Referrer-Policy: no-referrer` (the token is in the URL), and framed only by the same origin (sandboxed iframe without scripts).
- Slug availability answers yes/no only; the cross-workspace query is allow-listed (`*Queries.cs`).

## File uploads (R1-P1)

- Accepted by **magic bytes** only (JPEG, PNG, WebP), never by name or client content type; at most 5 MB, at least 128 × 128 px; image dimensions are read from the header and limited (6000 × 6000, 36 MP) **before** pixels are decoded (decompression bombs).
- Every image is decoded and **re-encoded** (SkiaSharp → WebP, ≤ 1024 px): EXIF (including GPS), comments and any appended payload are dropped; the EXIF orientation is applied first.
- Files live outside wwwroot (`Files:RootPath`) under generated keys (`{workspaceId}/{fileId}.webp`), with path-traversal checks and no overwrites; metadata rows are tenant-owned with composite tenant FKs.
- Photos are served only through an authorized endpoint (`ws:profile.read`), never publicly cacheable, with `nosniff`; the public variant (`/{slug}/photo`) exists only while the published site's hero shows it (R1-P4).
- Uploads use the same antiforgery header as every unsafe request (no automatic form antiforgery binding).

## E2E environment safety (R0-P7)

- The `E2E` environment is the only one that migrates at startup, and only after `E2EDatabase.AssertDisposable` accepted the connection string: database `ClassHubE2E_*`, loopback TCP endpoint with an explicit port, no Windows authentication (tested with the local connection string, named instances, LocalDB and remote hosts).
- The dev mailbox API and its SPA page are mapped only in Development, Testing and E2E (integration test for Production and Staging).

## Tenant isolation (R0-P5)

A teacher's **workspace** is the tenant. Layers (each tested):

| # | Layer | Implementation | Test |
|---|---|---|---|
| 1 | Routing + policy | Workspace APIs live under `/api/w/{workspaceId:guid}`; `WorkspacePermissionHandler` checks an active membership and the role's permission | `WorkspaceTenancyTests` |
| 2 | Context | The handler binds the request to the verified workspace (`TenantContext.Set`, once; a request cannot switch workspaces). Never read from headers or bodies | `TenancyUnitTests` |
| 3 | Reads | EF Core 10 named query filter `Tenant` on every `ITenantOwned` entity: `WorkspaceId == CurrentTenantId`; **no tenant → no rows** | `TenancyProbeTests`, `WorkspaceTenancyTests` |
| 4 | Writes | `TenantSaveChangesInterceptor`: inserts are stamped with (or must match) the current workspace; updates/deletes must target it; `WorkspaceId` never changes; outside a workspace request new rows need an explicit WorkspaceId | `TenancyProbeTests` |
| 5 | Database | Composite tenant FKs `(WorkspaceId, ParentId) → (WorkspaceId, Id)` via `HasTenantReference`; the database rejects cross-workspace links even if code is wrong | `TenancyProbeTests` |
| 6 | Bypass control | `IgnoreQueryFilters` and raw SQL only in allow-listed files (`*Queries.cs` in module `Persistence`, migrations, the outbox dispatcher, `Jobs/`) | `TenantBypassTests` |
| 7 | Output | Explicit response DTOs; entities are never serialized | review |
| 8 | Tests | `TenantIsolationKit.AssertCrossTenantDeniedAsync`: another teacher gets **404 `NOT_FOUND`** (never 403) and changes nothing; every new tenant resource adds these tests | `WorkspaceTenancyTests` |
| 9 | Audit | Append-only `AuditLog` (actor, action, target, workspace, before/after JSON, request id) for workspace creation, settings changes and platform role grants; no secrets or emails in details | `WorkspaceTenancyTests` |

Registration provisions the workspace and Owner membership **in the same transaction** as the account and its confirmation email (tested: a failing provisioning leaves no account and no email).

## Logging and errors

Secrets are redacted and emails masked in logs; error responses never contain exception details (R0-P3, see ARCHITECTURE.md).

## Accepted local risks

- Development runs as the developer's Windows account (sysadmin) against `.\SQLEXPRESS`; a least-privilege runtime identity comes with hosting (D-28).
- Codex reviews run locally; CI checks the signed, commit-bound evidence but cannot execute Codex itself.
